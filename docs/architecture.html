AIOps Observability Platform

Architecture, high-level design (HLD), and low-level design (LLD) for the deployed demo and AIOps portal. This document describes the running implementation in the aiops repository, including its host-specific deployment overlay.

1 VM · Docker Compose15 containersOpenTelemetry + GrafanaClickHouse analyticsHTTPS via Caddy

1. Scope and status

The system generates e-commerce traffic, collects telemetry, presents it in Grafana, and analyzes it in a separate AIOps portal.

Public interface

AIOps portal

aiops.iohtechco.com serves the static Next.js UI and proxies /api/* to FastAPI.

Public interface

Grafana

grafana.aiops.iohtechco.com presents provisioned dashboards, metrics, logs, and traces.

Deployment mode

Existing host

The production overlay uses an external ClickHouse instance and preserved Docker volumes from the previous two Compose projects.

Scope boundary. This is a demo-specific platform. The AIOps queries are coupled to the otel schema, specific service names, and order/payment/inventory metrics. A generic multi-source or multi-tenant AIOps platform has not yet been implemented.

Logical arrows show the main relationships; exact protocol and port assignments appear below. ClickHouse and Gemini are outside the VM Compose network in the current deployment.

3. High-level design (HLD)

Presentation plane

Portal and Grafana

Caddy terminates HTTPS and routes by hostname. The portal's Nginx serves exported Next.js files and forwards /api/ to FastAPI. Grafana queries its provisioned Tempo, Prometheus, and Loki data sources.

Workload plane

Demo transaction path

The load generator calls Order. Order calls Inventory and Payment, then writes successful orders to PostgreSQL. Inventory caches simulated stock in Redis. Payment includes deliberate and random failure scenarios.

Telemetry plane

Collection and storage

Instrumented services export OTLP to the Collector. It fans out traces to Tempo and ClickHouse, metrics to a Prometheus scrape endpoint and ClickHouse, and logs to Loki and ClickHouse. Node Exporter is scraped by the Collector.

Intelligence plane

AIOps analysis

FastAPI reads ClickHouse over HTTP to compute forecasts, anomaly timelines, log templates, trace shapes, service dependencies, and cross-signal views. Chat and incident summaries call Gemini when configured.

Design decisions visible in the implementation

  • One Docker Compose project and one bridge network connect the VM services; no Kubernetes, message broker, or separate API gateway is present.
  • Grafana is a visualization path; the AIOps portal reads ClickHouse directly and does not query Grafana's API for analytics.
  • The frontend is statically exported at build time and served by Nginx. Browser API calls use relative /api paths, so the same HTTPS origin serves UI and API.
  • The host deployment keeps historic Tempo, Prometheus, Loki, Grafana, and CmdStan volumes. A local-only Compose mode can instead start the repository's ClickHouse service.

4. End-to-end data flows

4.1 Order and telemetry sequence

1 · TriggerLoad generator or client sends POST /orders.
2 · InventoryOrder calls GET /stock/{item_id}; Inventory checks Redis and simulated stock.
3 · PaymentOrder calls POST /charge; Payment may accept or reject.
4 · PersistSuccessful orders are stored in PostgreSQL.
5 · ObserveSpans, logs, and metrics reach the Collector and fan out to stores.

OpenTelemetry trace context follows the HTTP calls. Manual spans mark inventory lookup, payment, and order database steps. Trace IDs also appear in logs, enabling log-to-trace navigation in Grafana.

4.2 Grafana query path

Browser → Caddy → Grafana. Grafana queries Prometheus for metrics, Loki for logs, and Tempo for traces. Provisioned data-source links connect related logs, traces, and metrics. Tempo's metrics generator writes span and service-graph metrics to Prometheus remote write.

4.3 AIOps query path

Browser → Caddy → frontend Nginx /api/ → FastAPI router → ClickHouse otel tables → JSON result → portal component. Forecast and anomaly requests run models synchronously in the API process. Health checks run SELECT 1 against ClickHouse.

4.4 AI request path

For chat, FastAPI sends a schema-aware prompt and recent conversation to Gemini 2.5 Flash. If the model returns a SQL SELECT, the backend executes it against ClickHouse and can send a small result subset back to Gemini for interpretation. For incident summaries, FastAPI first gathers errors, slow spans, logs, and metric totals, then sends that context to Gemini.

Demo service APIs

POST /orders orchestrates stock and payment; GET /stock/{item_id} and GET /stock expose inventory; POST /charge simulates payment. Each service exposes /health and /metrics. Demo controls include DELETE /cache/{item_id}, GET /demo/scenarios, and GET /demo/failure-rate.

Frontend modules

The portal has Predictive, Detective, Diagnostic, and Chat pages. React components call the matching API routes; useHealthCheck polls the health route. There is no browser-side database connection or Gemini key.

10. Security and trust boundaries

Implemented

Transport and secrets

Caddy terminates public TLS and redirects HTTP to HTTPS. ClickHouse credentials, Grafana admin bootstrap password, and Gemini key are supplied from an ignored .env file. Caddy stores ACME certificates in a persistent Docker volume.

Current exposure

Access control

Grafana permits anonymous Viewer access. The portal and FastAPI have no application authentication. Legacy direct host ports remain published alongside the HTTPS names. Internal Compose traffic is HTTP/gRPC without TLS.

Security review items before general use. The backend currently allows all CORS origins; some SQL statements interpolate request parameters directly, and chat checks only whether extracted SQL starts with SELECT. Gemini and HTML formatting should be treated as untrusted-output boundaries. Add authentication, authorization, strict query validation/parameterization, output escaping, rate limits, and network exposure controls before using this with sensitive or multi-tenant telemetry.

For this VM, both Compose files are required. Do not remove volumes during a restart. Caddy needs inbound 80/443 and persistent certificate storage for automated renewal. If ClickHouse is unavailable, the portal can load but analytics and health report database failure; Grafana's Tempo/Prometheus/Loki views can remain available independently.

12. Constraints and next design steps

  1. Generic AIOps abstraction: replace fixed otel table names, metric names, and demo service identities with discoverable schemas and configured source adapters.
  2. Access model: introduce identity, tenant boundaries, read-only database credentials for analytics, and a constrained query service before wider rollout.
  3. Workload management: move long forecasting and AI tasks out of synchronous API requests if usage grows; add timeouts, queues, caching, and job status.
  4. Durability: formalize PostgreSQL/Redis persistence and backup policy if the demo transaction data becomes important.
  5. Deployment reproducibility: the current VM overlay reuses Python images built by the older projects. Build and publish versioned images from this repository for future hosts.
  6. Availability: the present deployment is one VM and one instance per service. It has no load-balanced failover or disaster-recovery automation.
